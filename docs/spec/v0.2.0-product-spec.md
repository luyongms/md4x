# md4x v0.2.0 — Product Spec

*A semi-WYSIWYG markdown editor wrapped around the v0.1.x rendering
kernel. Cross-platform via Tauri. Single-document, single-window MVP.*

---

## 1. Problem

md4x v0.1.x is a CLI: a writer edits markdown in their preferred editor,
runs `md4x foo.md`, opens the resulting PDF in Preview, and sees what
the published page looks like. The render is high-fidelity — magazine-
quality typography, math, mermaid, syntax-highlighted code — but the
*loop* is slow. Every iteration is "edit → save → switch terminal →
re-run → switch viewer → judge." Two or three context switches per
iteration. After ten edits, the writer is tired of the workflow and
ships a worse document.

Existing tools (Typora, Obsidian, MarkText, iA Writer, MacDown) close
the loop with a live preview pane, but treat PDF export as an
afterthought — output quality varies from passable to dismissive. None
of them target *magazine-grade typography* as the primary outcome.

md4x's wedge: **the PDF is the product, and the editor is the on-ramp
to producing it well.**

## 2. Target user

A writer who:

- Drafts in markdown by preference (engineer, researcher, journalist,
  technical writer, designer who blogs).
- Cares enough about typography to notice when it's wrong.
- Wants a final artifact that looks like it came from a publishing
  house, a textbook, a magazine, or a manifesto — not a generic
  markdown-to-PDF dump.
- Is comfortable installing a desktop app and opening a Chrome window
  in the background (we don't bundle a browser).

Not the target user:

- Someone collaborating in real time with multiple authors.
- Someone publishing primarily to the web (a static-site generator
  serves them better).
- Someone who wants an outline-driven, link-graph-driven knowledge
  base (Obsidian / Logseq territory).

## 3. v0.2.0 goals

The release earns its number if a writer can:

1. **Open a markdown file** and see a styled preview within ~500 ms of
   first paint.
2. **Type and watch the preview update** within ~300 ms of stopping
   typing, without dropping a frame on edits to a 10-page document.
3. **Switch templates** from a single dropdown and see the entire
   preview restyle in under a second, with no document edit.
4. **Export to PDF** via one button or `Cmd-E` and get the same byte
   output the v0.1.x CLI would produce.
5. **Save / Save As / Open** files via OS-native file dialogs and
   `Cmd-S` / `Cmd-Shift-S` / `Cmd-O`.
6. **Recover** sensibly from broken markdown (bad mermaid, malformed
   math) — preview keeps rendering everything else; broken blocks show
   a small inline error, not a blank page.

If any of those isn't true on a 10-page document with mermaid + math +
code, v0.2.0 isn't ready to ship.

## 4. Non-goals (deliberately punted)

- **Multiple documents per window or multi-window.** One window, one
  document. Open another file → same window, current document
  replaced (with unsaved-changes prompt).
- **Real-time collaboration.** No CRDTs, no shared cursors.
- **Cloud sync, version history, project management.** Files live on
  disk. Git is the version control.
- **Custom theme editor.** Users pick from shipped templates (six in
  v0.2.0); they don't write CSS in the GUI.
- **Outline view, backlinks, tag pane.** Markdown source pane only.
- **WYSIWYG editing of styled output.** Source pane is plain markdown.
  The "semi" in semi-WYSIWYG is honest: the *preview* is WYSIWYG, the
  *editor* is markdown source.
- **Per-page page-numbered preview.** Preview shows content as a
  continuous scrolling document. Page-level effects (running headers,
  page breaks, page numbers) only appear in the exported PDF. (See
  §7.1 — possible v0.3 feature.)
- **Plugin store / extension marketplace.** v0.1.2 has a plugin
  architecture internally; surfacing it to end users is out of scope.
- **Auto-update.** v0.2.0 is dist via tarball + manual install. Auto-
  update is a v0.2.x stretch.

## 5. User stories

### US-1: First-run drafting (primary)

> *As a writer starting a new article, I want to launch md4x, paste my
> markdown into the editor, watch the preview render with a chosen
> template, and iterate until the typography feels right — all
> without leaving the app.*

Acceptance:
- Launch app → empty editor on the left, empty preview on the right.
- Paste markdown → preview updates within 300 ms of paste.
- Click template dropdown → 6 names visible, current one highlighted.
- Pick a different template → preview restyles within ~1 s.
- Click "Export PDF" → file dialog opens with a sensible default
  filename; selecting a path writes the PDF.

### US-2: Open existing file

> *As a writer with an existing `.md` on disk, I want to open it in
> md4x and edit it in place.*

Acceptance:
- `Cmd-O` or `File → Open` opens an OS-native file picker filtered to
  `.md` / `.markdown`.
- Selected file's content fills the editor; preview renders.
- `Cmd-S` writes back to the same path, no re-prompt.
- `Cmd-Shift-S` opens "Save As" dialog with the current filename
  pre-filled.
- The window title shows the filename; an unsaved-changes indicator
  (e.g. trailing `•`) appears after first edit.

### US-3: Iterate on diagrams

> *As an architect drafting a design doc, I want to write mermaid
> blocks and see the rendered diagram in the preview without
> re-running anything.*

Acceptance:
- Type ```` ```mermaid ```` block → preview shows rendered diagram
  within ~500 ms of finishing typing.
- Edit the diagram → preview re-renders that diagram only (others
  cached and untouched).
- Diagram with syntax error → shows an inline error message in
  preview, not a blank.

### US-4: Iterate on math

> *As a researcher writing equations, I want inline `$...$` and
> display `$$...$$` math to typeset live as I type.*

Acceptance:
- Inline `$\vec{v}$` typesets within 300 ms of stopping typing.
- Multi-line `$$...$$` block typesets, with the bare-`=` bug from
  v0.1.1 already fixed (regression test still passes).
- Bad LaTeX (e.g. unclosed `\frac{`) shows the source in red, not
  a crashed preview.

### US-5: Recover from a broken document

> *As a writer who pasted unfinished content, I want the preview to
> keep working — show me what's good, mark what's broken.*

Acceptance:
- Unclosed code fence → preview marks the rest of the doc as one big
  code block (CommonMark behavior); doesn't crash.
- Malformed mermaid → that block shows an error pill; rest of doc
  renders normally.
- Malformed KaTeX (with `throwOnError: false`) → shows source in
  red; rest of doc renders.
- Empty file → empty preview, no error popup.

### US-6: Export quality matches CLI

> *As a writer who used the CLI before, I want the GUI's "Export PDF"
> button to produce the exact same output as `md4x foo.md`.*

Acceptance:
- For any `.md`, GUI's exported PDF has the same byte-equivalent
  content as the CLI's output (modulo timestamp metadata, which
  Chrome embeds).
- Same templates, same plugin pipeline, same Chrome flags.

## 6. Success criteria (measurable)

A v0.2.0 build is shippable when:

| Criterion | Target |
|---|---|
| Cold-start app launch (binary → editable window) | < 1.5 s on Apple Silicon |
| First preview paint after opening a file | < 500 ms |
| Preview update latency from last keystroke | < 300 ms p50, < 700 ms p95 |
| Template switch latency | < 1 s |
| PDF export latency (10-page doc) | < 5 s |
| App memory footprint, idle, 1-page doc | < 200 MB |
| App memory footprint, 50-page doc loaded | < 500 MB |
| App bundle size (.app or installer) | < 15 MB |
| Crash-free sessions on a 10-iteration test plan | 100% |
| Fully offline operation | yes (no network calls during render) |

If we miss any of those, we hold the release.

## 7. Open questions

### 7.1 Page-level preview vs. content-only preview

The cheap thing is a "content-only" preview: render the body HTML,
apply the template's CSS, scroll continuously. No page breaks, no
running headers, no page numbers. This is what every other markdown
editor does.

The honest, harder thing is a "page-level" preview that shows actual
A4 page boundaries, running headers, and page numbers — what the PDF
will look like, page-by-page. paged.js or a custom CSS Paged Media
polyfill could do this. Cost: significant frontend complexity, slower
re-render, scrolling weirdness.

**v0.2.0 decision:** content-only preview. Defer page-level to a
future v0.2.x or v0.3.0. The tradeoff is honest in the name
("semi-WYSIWYG").

### 7.2 Editor pane: vanilla `<textarea>`, contenteditable, or CodeMirror?

- **`<textarea>`**: zero dependencies, works everywhere, no
  syntax-highlighted markdown source.
- **CodeMirror 6**: ~200 KB gzipped, gives markdown syntax
  highlighting, line numbers, search/replace, multi-cursor. Industry
  standard.
- **contenteditable**: fragile, varies across webviews, would let us
  do limited inline formatting (the path to true WYSIWYG someday).

**v0.2.0 decision:** start with vanilla `<textarea>` for MVP, switch
to CodeMirror 6 in v0.2.1 once the core loop is solid. Reasoning: the
core value is the *preview*, not the editor; we shouldn't burn week 1
on editor polish.

### 7.3 Multi-window / multiple documents

A real text editor supports `Cmd-N` for a new window. We don't, in
v0.2.0. Single-window forces us to focus.

**v0.2.0 decision:** one window. Future-compatible: the kernel is
already a library and a Tauri shell can spawn multiple windows when
we want it.

### 7.4 Drag & drop a `.md` onto the dock icon

macOS users expect this. Tauri supports it via the `tauri::Window`
event API.

**v0.2.0 decision:** support drag-drop and "open with md4x" from
Finder for `.md` files. Required for a normal-feeling app.

### 7.5 Distribution

- Tarball: simple, what the CLI uses today.
- `.dmg` with the app bundle: macOS-native, requires code-signing
  ($99/year Apple Developer cert) for clean install on others'
  Macs.
- Auto-update: `tauri-plugin-updater` exists and works well.

**v0.2.0 decision:** ship a `.dmg` with code signing if you (the
user) opt into the cert; otherwise tarball with `xattr -d
com.apple.quarantine` instructions in the README, same as today.
Auto-update is a v0.2.x feature.

## 8. Risks

### 8.1 WKWebView quirks

We're embedding KaTeX and mermaid.js inside a system webview. macOS's
WKWebView is mostly Safari, but with some sandbox differences. KaTeX's
font-loading via `@font-face` from a `data:` or `file:` URL has been
known to glitch in WKWebView. Test early, fall back to inline `<svg>`
math if it bites.

### 8.2 Mermaid re-render performance on diagram-heavy docs

A 30-mermaid document re-running mermaid.initialize on every preview
update is a bad time. Mitigations:
- Debounce preview updates (250 ms idle window).
- Cache rendered SVGs by `hash(source)`; only re-run mermaid for
  blocks whose source changed.
- Render mermaid blocks asynchronously; the rest of the page paints
  immediately.

### 8.3 macOS code signing & notarization

Without an Apple Developer cert, distributed builds need the
`xattr -d com.apple.quarantine` workaround. With one, dmg installs
cleanly on first try. $99/year is real money for an experimental
project.

**Plan:** ship unsigned to the user's friends in v0.2.0; revisit
signing when there's a stable user base.

### 8.4 Tauri version churn

Tauri 2.0 just stabilized in 2024. Plugin APIs may evolve. Pinning
the version in `Cargo.toml` and treating Tauri upgrades as a
deliberate task (not background dependency drift) is the safe
default.

### 8.5 Chrome dependency persists

The PDF export still shells out to headless Chrome. We did this
deliberately for v0.1.x and that decision still holds. The GUI
does not change it. Document clearly: "md4x.app needs Chrome on
your machine for PDF export."

## 9. Phased rollout inside v0.2.x

| Phase | What lands | When |
|---|---|---|
| v0.2.0 | Workspace restructure → md4x-core / md4x-cli / md4x-gui (Tauri scaffold + 3 commands + textarea-and-iframe MVP). Open / Save / Save-As / Export PDF / template switcher. Debounce + mermaid cache. | First releaseable GUI |
| v0.2.1 | CodeMirror 6 editor pane (markdown syntax highlighting, search, line numbers). | Editor polish |
| v0.2.2 | Drag & drop, recent-files menu, settings persistence (chosen template default, debounce window, dark/light editor chrome). | Normal-app polish |
| v0.2.3 | Auto-update via `tauri-plugin-updater`; signed dmg if cert acquired. | Distribution polish |
| v0.3.0 | Page-level preview (paged.js or equivalent). Multi-window. | Bigger structural step |

## 10. Out-of-band: what we're *not* deciding here

The internal architecture of the v0.2.0 GUI shell — the workspace
layout, Tauri command contract, frontend pipeline, build setup —
lives in the design spec at
`docs/spec/v0.2.0-design-spec.md`. That doc decides "how"; this one
decides "what" and "for whom."
