# md4x v0.2.0 — Design Spec

*Implementation contract for the Tauri GUI shell. Pairs with
`docs/spec/v0.2.0-product-spec.md` (what + for whom) and
`docs/spec/v0.2.0-workspace-restructure.md` (the crate split).*

---

## 1. Architecture in one diagram

```
┌─────────────────────────────────────────────────────────────────┐
│  md4x-gui  (Tauri shell — bin)                                  │
│                                                                 │
│  ┌──────────────────────┐    IPC (Tauri commands)  ┌─────────┐  │
│  │  frontend (webview)  │ ───────────────────────▶│ Rust    │  │
│  │  HTML / CSS / JS     │                         │ backend │  │
│  │  - editor pane       │ ◀───────────────────────│         │  │
│  │  - preview iframe    │    (HTML, paths, …)     └────┬────┘  │
│  │  - template chooser  │                              │       │
│  └──────────────────────┘                              │       │
│                                                        ▼       │
│                                          ┌──────────────────┐  │
│                                          │  md4x-core       │  │
│                                          │  (lib)           │  │
│                                          │  - render        │  │
│                                          │  - plugins       │  │
│                                          │  - templates     │  │
│                                          └──────────────────┘  │
└─────────────────────────────────────────────────────────────────┘
```

Three rules:

1. **The kernel knows nothing about the GUI.** `md4x-core` is the same
   library `md4x-cli` already uses; the GUI is a third caller.
2. **No rendering happens in the frontend.** The frontend asks the
   backend for HTML; it doesn't run comrak. KaTeX and mermaid.js *do*
   run in the webview (they always have, even for the CLI's PDF
   export — Chrome runs them at print time).
3. **No file I/O happens in the frontend.** Tauri commands take/return
   strings and paths; reads/writes go through the Rust backend.

```
crates/

    └── frontend/
```

The repo-root `mermaid.min.js`, `katex/`, and `templates/` move into
`crates/md4x-core/` so `include_bytes!` / `include_dir!` paths stay
relative to the crate that uses them.

## 3. Tauri command contract

All IPC between frontend and backend goes through three commands. They
are the *complete* interface; we do not invent ad-hoc message types
later.

### 3.1 list_templates

```rust
#[tauri::command]
fn list_templates() -> Vec<String> {
    md4x_core::templates::available()
        .iter().map(|s| s.to_string()).collect()
}
```

Called once at app startup to populate the template dropdown. Returns
`["magazine", "swiss", "stem", "tufte", "newyorker", "brutalist"]` in
v0.2.0; future-proof — the frontend doesn't hardcode names.

### 3.2 render_html

```rust
#[derive(Serialize)]
struct RenderedDoc {
    /// Self-contained HTML — `<style>` + body + KaTeX/mermaid scripts inlined.
    html: String,
    /// Diagnostics from the render (mermaid parse errors, etc.) for an
    /// inline error surface in the preview.
    diagnostics: Vec<String>,
}

#[tauri::command]
fn render_html(md: String, template: String) -> Result<RenderedDoc, String>;
```

The single hot path. Frontend calls this on every (debounced) edit and
on template change. Backend:

1. Strips BOM, runs `Registry::default().preprocess_markdown(&md)`.
2. Renders via `md4x_core::render::markdown_to_html_with(&md, &registry)`.
3. Loads `templates::style_css(&template)` and `templates::cover_html()`.
4. Substitutes cover values (the same path as PDF export).
5. Concatenates: `<style>{css}</style>` + cover + body, plus `<script>`
   tags for `mermaid.min.js` and `katex.min.js` served from
   bundled-into-binary bytes via a Tauri custom-protocol handler.
6. Returns the HTML to the frontend, which assigns it to the preview
   iframe via `iframe.srcdoc`.

Errors are returned as `Err(String)` for fatal failures (e.g. unknown
template). Per-block failures (mermaid parse error) come back as
`diagnostics` and the render still succeeds.

### 3.3 export_pdf

```rust
#[tauri::command]
fn export_pdf(md: String, template: String, output: PathBuf) -> Result<u64, String> {
    // Write md to a temp file in the same dir as `output` so relative
    // image paths resolve, then delegate to md4x_core::render::render_pdf.
    // Returns final PDF size in bytes.
}
```

Drives the same `render_pdf` the CLI uses, so output is byte-equivalent
(modulo Chrome's embedded timestamp). The frontend calls this when the
user clicks "Export PDF" or hits `Cmd-E`. The backend handles file
dialog → path resolution → render → return size for a "Wrote 1.2 MB"
toast.

### 3.4 What's *not* a command

- No `read_file` / `write_file` — file ops use Tauri's
  `tauri-plugin-dialog` and `tauri-plugin-fs` directly from Rust.
- No `save_settings` — settings persistence goes through
  `tauri-plugin-store` (or `tauri-plugin-config`), not custom commands.
- No `register_template` — templates are still `cargo`-time builtins
  in v0.2.0.

## 4. Frontend architecture

Vanilla HTML / CSS / JS — no framework, no bundler. Reasoning: the
frontend is small (~300 lines), framework choice is a religious
decision better deferred, and Tauri 2 supports zero-build frontends out
of the box.

### 4.2 Why iframe srcdoc for the preview — and the no-flash invariant

The preview document needs to load *the template's CSS* and *KaTeX +
mermaid scripts* in an isolated style world. If we mounted it into the
main DOM, the editor's own styles would bleed into the preview (or vice
versa) and we'd be debugging cascade specificity instead of writing
features. So: an iframe is the right boundary.

But **the iframe is loaded exactly once per template** — not once per
keystroke.

#### The no-flash invariant (HARD RULE)

> **The preview pane must NEVER visibly blank, white-flash, or
> full-repaint on edit-driven re-renders.** Every keystroke-induced
> render is applied as a minimum-edit DOM patch against the existing
> preview document. Full reloads happen only on template switch and
> are hidden behind a fade-swap (§6).

Reason: this is md4x's wedge. The whole pitch is "type on the left,
watch the magazine retypeset on the right." If "retypeset" looks like
a strobe light — the way MacDown does it — the wedge dies on contact.
A user described MacDown's behavior verbatim as *"obviously not doing
double-buffering or the like. we should avoid that. this is a UX killer."*

The cheap pattern (`preview.srcdoc = html` on every render) is
explicitly forbidden in v0.2.0. It is *not* an acceptable MVP that we
optimize later — it would ship a broken core experience and require
rewriting the render path under user complaints.

#### How the pattern works

```
JS pseudocode:
    // ONCE on app start (and on template change, see §6):
    preview.srcdoc = bootstrapHTML(template)
    await preview.onload
    previewDoc = preview.contentDocument

    // EVERY edit-driven render:
    rendered = await invoke('render_html', {md, template})
    newDoc   = new DOMParser().parseFromString(rendered.html, 'text/html')
    morphdom(previewDoc.body, newDoc.body, {
        onBeforeElUpdated: skipIfBlockHashUnchanged,
    })
    // scroll position, mermaid SVGs, KaTeX nodes all preserved
    // because the nodes themselves were never destroyed
```

Implementation choice: **morphdom** (≈3 KB, MIT, no deps) is the
reference library. Alternatives: nanomorph, set-dom. The exact pick
is decided in Phase C; the contract is "diff-and-patch, no full
replacement on edit."

Properties this gives us for free:

- **Scroll position is preserved** — we never touch the scroll
  container, so the browser doesn't reset it.
- **Mermaid SVGs survive** — if the source markdown for a mermaid
  block hasn't changed, its DOM subtree is bit-identical and morphdom
  short-circuits via `onBeforeElUpdated` returning false.
- **KaTeX nodes survive** — same mechanism, keyed on math-span hash.
- **Selection survives** — if the user is hovering or has selected
  text in the preview, mid-typing doesn't blow it away.
- **GPU layers stay warm** — the browser keeps composited layers; no
  white-frame between repaints.

#### Block-hash skip mechanism

Backend (`render_html`) emits each `<pre class="mermaid">`,
`.katex-block`, `pre code`, and other heavy block with a stable
`data-md4x-hash="..."` attribute computed from the block source.
Frontend's morphdom hook reads `data-md4x-hash`; if old and new match,
returns `false` to keep the existing subtree untouched.

This is how we get the perf win (no re-render) AND the visual
calmness (no DOM churn) from the same mechanism.

#### Verification

Before v0.2.0 ships, the preview must pass this manual test: type
continuously into the editor for 30 seconds with a 30-mermaid doc
loaded. Record screen. Frame-step through. **Zero white frames, zero
mermaid re-renders for unchanged blocks, zero scroll jumps.**

### 4.2.1 Scaling note: long documents

For typical md4x docs (5–20 pages — essays, design specs, reports),
the morphdom path runs in 30–60 ms wall-clock per debounced edit.
Feels instant.

For 100-page outliers, the same path costs ~150–200 ms. Noticeably
laggy when typing, but **the no-flash invariant still holds** (the
DOM tree is patched, never replaced) — and that's the load-bearing
property. Latency on a 100-page edit is acceptable; visual flashing
is not.

If long-doc latency ever becomes a real complaint (dogfooding will
tell us), the optimization is **server-side block-delta**: backend
remembers last-render block hashes, emits a small `Vec<DocOp>`
instead of a full HTML body, frontend applies ops directly without
DOMParser+morphdom. This was considered for v0.2.0 and rejected
because:

- One consumer (the GUI). Not enough cases to justify a new layer.
- morphdom is JS-native and battle-hardened; a homegrown block-diff
  isn't.
- A future web shell (if there ever is one) would use morphdom too —
  it's the natural fit for HTML DOM, not a Rust-side diff.

If we ever build it: as a module *inside* `md4x-gui` (not a separate
crate), with a `Vec<DocOp>` IPC contract replacing `render_html`.
morphdom stays as the wholesale-fallback applier.

Not in v0.2.0.

### 4.3 Mermaid + KaTeX caching

Caching exists for two reasons that compound:

1. **Perf:** every keystroke re-runs every mermaid render otherwise.
   30-mermaid doc → hundreds of ms per edit.
2. **No-flash invariant (§4.2):** even if mermaid rendered instantly,
   replacing an existing SVG with a freshly-built identical SVG causes
   a visible flicker as the browser drops and re-creates layout.
   Skipping the work also skips the flicker.

Cache strategy lives in two places:

**Backend** (`render_html`): emits `data-md4x-hash="<hex>"` on each
mermaid / math / code block, where `<hex>` is a stable hash of the
block source. Cheap; lets the frontend short-circuit without
re-parsing source.

**Frontend** (inside the iframe):

```
mermaidCache:  Map<hash, SVGElement>    // detached SVG nodes
mathCache:     Map<hash, HTMLElement>   // detached KaTeX nodes

afterMorphdom():
    for each <pre class="mermaid"> with data-md4x-hash=h:
        if it already has a rendered SVG child (morphdom kept it), skip
        else if mermaidCache.has(h):
            adopt cached SVG into this <pre> via importNode
        else:
            queue mermaid.render() in next idle frame
            on result: cache by h, adopt into <pre>

    same shape for math
```

Three rules baked in:

- Cache lookup happens *after* morphdom, not before. If morphdom kept
  the existing subtree (because hash matched), there's nothing to do.
- Cache miss does NOT block paint. Render mermaid in
  `requestIdleCallback` so the unchanged parts of the preview update
  immediately and new diagrams fill in within a frame or two — never
  freeze the editor on a slow render.
- Cache is per-template-instance. Switching templates wipes the cache
  because diagrams inherit template colors/sizes.

### 4.4 Debouncing

Edit-to-render path:

```
on input event:
    cancel any pending render
    schedule render in 250ms:
        invoke('render_html', {md, template}) → applyToPreview
```

250 ms idle window. Configurable in v0.2.x via settings; hardcoded for
MVP.

## 5. Live preview pipeline

Edit → render in milliseconds, with the **no-flash invariant** (§4.2)
preserved end-to-end:

```
keystroke
   │
   │  (250 ms idle)
   ▼
invoke('render_html', {md, template})
   │
   │  IPC ⇢ Rust
   ▼
md4x_core::render::markdown_to_html_with(md, registry)
   │  ~5–20 ms for a 10-page doc
   │  emits data-md4x-hash on each heavy block
   ▼
templates::style_css(template) + templates::cover_html()
   │  ~ms (CSS already loaded in iframe; only body changes)
   ▼
HTML body string
   │  IPC ⇡ JS
   ▼
DOMParser → newBody
   │
   ▼
morphdom(previewDoc.body, newBody, skipUnchangedHashedBlocks)
   │  in-place patch; existing SVGs/math/scroll preserved
   ▼
afterMorphdom: fill cache misses for new mermaid/math
   │  via requestIdleCallback — never blocks paint
   ▼
PAINT (calm; no white frame)
```

p50 budget: 100 ms backend, 50 ms IPC, 50 ms morphdom diff =
**~200 ms perceived**.
p95 budget: 700 ms (heavy mermaid edit) — but the *unchanged* parts
of the preview update within the p50 window; only the new diagram
fills in late.

Forbidden in this pipeline:

- `preview.srcdoc = ...` after initial mount.
- `preview.contentDocument.body.innerHTML = ...`.
- `replaceChildren` on the body root.
- Anything that destroys mermaid/KaTeX nodes whose source hasn't
  changed.

## 6. Template switching

Template switching is the **one** place a full reload is permitted —
the CSS environment changes, so an in-place patch can't avoid a
visible restyle. To keep the no-flash invariant intact we hide the
reload behind a fade-swap with two iframes.

Pattern:

1. Two stacked iframes share the same grid cell. Only one is visible
   at a time (`opacity: 1` vs `0`, both with `position: absolute;
   inset: 0`).
2. User picks a new template.
3. Off-screen iframe gets the new `bootstrapHTML(newTemplate)` via
   `srcdoc`. Wait for `load`.
4. Off-screen iframe receives the freshly-rendered body (same
   morphdom path as §4.2, but starting from an empty body — it's
   really an initial population).
5. Off-screen iframe receives the cache adoption pass (§4.3).
6. Both iframes simultaneously animate opacity over ~150 ms (CSS
   transition); old fades out, new fades in. No white frame, no
   layout jump (both iframes occupied identical box geometry the
   whole time).
7. Old iframe is reset (or kept around for the next swap).

Mermaid + KaTeX caches are flushed when their owning iframe is reset,
not at swap time — old cache stays warm in case the user toggles back.

Latency target: < 600 ms total, with the *visible* transition pinned
at 150 ms regardless of how long step 4 takes. If step 4 runs long,
the swap is delayed but the user sees the old preview the whole time
— never a white iframe.

Forbidden: hot-swapping the `<link rel="stylesheet">` inside a single
iframe. It causes a flash of unstyled content (FOUC) before the new
sheet applies, exactly the failure mode this section exists to
prevent.

## 7. File operations

### 7.1 Open

```
Cmd-O → tauri-plugin-dialog::open() → user picks .md
       → Rust backend: fs::read_to_string + strip_bom
       → Tauri event "file:loaded" with {path, contents}
       → frontend: editor.value = contents; render
       → window title = basename(path)
```

### 7.2 Save / Save As

```
Cmd-S  → if no path: Save As. Else fs::write(path, editor.value)
Cmd-Shift-S → tauri-plugin-dialog::save() with default name
            → fs::write(picked, editor.value)
            → set current path = picked
```

Unsaved-changes indicator (`•` after filename in title bar): set on
every keystroke; cleared on successful save.

### 7.3 Export PDF

```
Cmd-E or button click
   → tauri-plugin-dialog::save() filtered to .pdf, default name
     `<input-stem>.pdf`
   → invoke('export_pdf', { md, template, output: picked })
   → on success: "Wrote 1.2 MB to /path" toast + reveal-in-Finder
   → on error: error toast with the kernel's error message
```

The kernel's existing scratch dir + chrome subprocess is unchanged.

### 7.4 Drag & drop

Tauri's `WindowEvent::FileDrop` carries a `Vec<PathBuf>`. v0.2.0
behavior: if a single `.md` dropped, treat as Open. Multi-file or
non-md: ignore.

### 7.5 Recent files

`tauri-plugin-store` persists a JSON list of paths under
`~/Library/Application Support/md4x/recent.json`. Cap at 10. Surfaced
in `File → Open Recent` submenu.

## 8. Settings persistence

`tauri-plugin-store` for everything user-configurable. Defaults built
into the binary; users override. Schema:

```json
{
  "default_template": "magazine",
  "preview_debounce_ms": 250,
  "split_position": 0.5,
  "recent_files": ["/path/a.md"],
  "window": { "x": 100, "y": 100, "w": 1200, "h": 800 }
}
```

Loaded at startup, written on changes (debounced 1 s).

## 10. Build & dist

### 10.1 Dev loop

```
cd crates/md4x-gui
cargo tauri dev
```

Tauri's dev command compiles the Rust backend, copies the frontend
files (no build step needed for vanilla JS), and opens a window with
hot reload on frontend changes.

### 10.2 Production build

```
cd crates/md4x-gui
cargo tauri build
```

Produces `target/release/bundle/macos/md4x.app` (and `.dmg` if
configured). Per-arch builds; we'll mirror the CLI's
`scripts/dist.sh` pattern with a separate `scripts/dist-gui.sh` for
arm64 / x86_64 dmg pairs.

### 10.3 Bundle size projection

| Component | Size |
|---|---|
| md4x-core (kernel + plugins + bundled assets) | ~7 MB (matches CLI bundled binary) |
| Tauri runtime + WebView2/WKWebView wrappers (Rust) | ~3 MB |
| Frontend (HTML/CSS/JS, vanilla) | ~30 KB |
| **Total `.app`** | **~10 MB** |

## 11. Testing strategy

### 11.1 Unit tests (Rust)

- Tauri commands (`list_templates`, `render_html`, `export_pdf`)
  tested as plain functions — Tauri's command macro lowers them to
  regular Rust functions, so we can call them directly with mock
  state.
- Reuses the kernel's existing 65-test suite unchanged.

### 11.2 Integration tests (Rust + Tauri test framework)

- App-launch smoke test: Tauri builds, window opens, no panics.
- Open-then-render smoke test: load a fixture `.md`, assert
  `render_html` returns HTML containing `class="cover-page"`.

### 11.3 Frontend tests

Out of scope for v0.2.0. The frontend is ~300 lines and the meaningful
behavior lives in the backend; manual testing via `cargo tauri dev` is
sufficient.

### 11.4 Performance regression

A small benchmark script that:
1. Spawns the dev build with a fixture doc loaded.
2. Triggers 100 simulated keystrokes.
3. Records the render-latency histogram.
4. Fails if p95 > 700 ms.

Each phase is independently buildable and testable. Phase A doesn't
ship anything user-visible (CLI behavior unchanged); phase F is the

## 13. Risks & mitigations (technical)

### 13.1 Iframe srcdoc + custom protocols

KaTeX / mermaid scripts need to load *inside* the preview iframe.
Options:
- Inline them into the srcdoc as `<script>` blocks (~3 MB inlined into
  the page string — bloats every IPC payload).
- Serve them via a Tauri custom protocol (e.g. `md4x://katex.min.js`)
  registered to read from the embedded bytes.

**Pick:** custom protocol. Each render's payload is just the doc HTML;
scripts are referenced by stable URLs the iframe loads once and caches.

### 13.2 Iframe scroll position

Solved by construction: the no-flash invariant (§4.2) means we never
replace `srcdoc` on edit, so the scroll container is never destroyed
and the browser never resets scroll. The morphdom diff path keeps the
same DOM tree, just patched.

Edge case: template switch (§6) does reload, but it lands in the
*off-screen* iframe and fades in — so the user sees the old preview's
scroll position until the swap, and the new iframe is initialized
with `window.scrollTo(0, savedScrollY)` before opacity flips.

### 13.3 Editor / preview clock skew

If the user types fast and the backend takes longer than the debounce
window, multiple renders queue up. We need to:
- Cancel in-flight render when a new one starts (Tauri's command
  cancellation isn't first-class; track a generation counter and
  ignore stale results client-side).

### 13.4 KaTeX font loading in WKWebView

WKWebView on macOS sometimes lazily loads `@font-face` woff2 files,
producing a flash-of-unstyled-math on first render. If observed,
preload via `<link rel="preload" as="font" crossorigin>` in the
preview head.

### 13.5 Content Security Policy & DOM injection

The preview iframe receives HTML built by the kernel and rendered SVG
from mermaid running inside the iframe. Both are trusted (we wrote
the renderer; mermaid runs sandboxed in the iframe), but we still
apply the principle of least privilege:
- The preview iframe sets a strict CSP allowing only scripts from
  our `md4x://` custom protocol.
- DOM updates inside the iframe use `replaceChildren` with parsed
  fragments rather than direct string-to-innerHTML where practical.
- Frontend → backend payloads are plain strings; nothing is `eval`d.

## 14. Backwards compatibility

- The CLI binary (`md4x-cli`) keeps its current name and behavior.
  Existing scripts that invoke `md4x foo.md` continue to work.
- The `templates/` directory layout is unchanged.
- The `bundle-templates` feature flag continues to work (used by both
  CLI and GUI dist builds).
- The kernel's library API is unchanged from v0.1.x for `render_pdf`,
  `markdown_to_html`, `extract_cover_values`, `substitute_cover`.

## 15. What's *out of scope* of this spec

- Specific frontend visual design (button colors, icon set, typography
  of the editor chrome). Decided during phase C; not load-bearing.
