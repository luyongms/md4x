# v0.2.4 — Line-level scroll anchoring

**Status:** spec locked. Companion to
`docs/spec/v0.2.4-self-contained-macros.md` in the same release.
**Layer:** GUI only (`crates/md4x-gui/frontend/app.js`,
`alignment-ticks.js`). No kernel, no plugin changes.

---

## 1. Problem

v0.2.3 anchors editor↔preview scroll sync at **block top**. The cursor's
red tick lands at the seam where its containing block begins. Inside a
multi-line block (paragraph, list item, code fence) every line maps to
the same anchor — scrolling one side past the block's first line lands
the other side at the same spot regardless of where the cursor or click
was.

Two consequences:

1. **Click in preview** mid-paragraph → editor cursor jumps to the
   block's first line, not the line under the click.
2. **Cursor move within a block** → preview anchor doesn't move.

Users expect line-level fidelity: clicking a paragraph in either pane
should land cursor + tick at the same conceptual position in the other.

## 2. Goal

Refine scroll sync from block-top alignment to **line-level**
alignment, using comrak's existing `data-sourcepos` and CodeMirror's
`lineBlockAt`.

Bidirectional:

- Editor cursor moves → red tick + preview scroll anchor at the
  cursor's line, not its block top.
- Click in preview → CodeMirror cursor lands at the inferred source
  line, then existing cursor-sync places editor + tick at that line.

## 3. Non-goals

- Pixel-perfect alignment in mixed-content blocks. Linear interpolation
  by source-line ordinal is the contract; math/mermaid/SVG blocks are
  approximate.
- Whole-document line-by-line tracking. We anchor at the **cursor's
  line** (single point of interest). Other ticks remain block-level.
- Replacing block-top sync entirely. Block-top remains the anchor when
  the cursor's containing block has only one source line (headings,
  thematic breaks, single-line code).

## 4. Mapping math

For each top-level block:

- Editor side: lezer block at index k spans `lBlocks[k].from` to
  `lBlocks[k].to` in source. Source lines L1..L2 from the same range.
- Preview side: `cache.blocks[k].el` carries
  `data-sourcepos="L1:Cs-L2:Ce"`. `cache.tops[k]` is the doc-Y of
  the element's top; `cache.blocks[k].el.offsetHeight` is its height.

For a target source line L (with L1 ≤ L ≤ L2):

```
fraction = (L - L1) / max(1, L2 - L1)        # clamp to [0, 1]

editorLineDocY  = cm.lineBlockAt(line.from).top
previewLineDocY = cache.tops[k] + fraction * cache.blocks[k].el.offsetHeight
```

Sync goal: place these two doc-Y values at the **same viewport
offset** on each side.

```
editorLineYInView  = editorLineDocY  - editor.scrollTop
previewLineYInView = previewLineDocY - preview.scrollY

# Editor → preview: choose preview.scrollY so previewLineYInView ==
#                   editorLineYInView.
preview.scrollY = previewLineDocY - editorLineYInView

# Preview → editor: choose editor.scrollTop so editorLineYInView ==
#                   previewLineYInView.
editor.scrollTop = editorLineDocY - previewLineYInView
```

Both sides clamp to their valid scroll range (existing helpers).

## 5. Behavior contract

### 5.1 Cursor in editor

When CodeMirror's selection-set update fires (cursor moved):

1. Find cursor's lezer block ordinal k via `lezerBlockIndexAtPos`.
2. Compute editor line doc-Y via `cm.lineBlockAt(cursor.head).top`.
3. Look up cache.blocks[k], read `el.dataset.sourcepos` for L1, L2.
4. Compute fraction; compute previewLineDocY.
5. Set preview scrollY = previewLineDocY − (editorLineDocY −
   editor.scrollTop). Smooth scroll.

The red tick on each side is rendered at the line's viewport-Y
(matching, by construction).

### 5.2 Click in preview

In `attachIframeHandlers` `click` listener (replaces current
`syncEditorFromPreviewClick` block-level logic):

1. Walk up from `e.target` to the top-level body child.
2. Read `data-sourcepos` for L1, L2.
3. Click-Y inside element = `e.clientY - rect.top`.
4. Source-line interpolation:
   `L = round(L1 + (clickY / rect.height) * (L2 - L1))`,
   clamped to `[L1, L2]`.
5. Compute the doc position at column 0 of line L.
6. CodeMirror dispatch: `selection: EditorSelection.cursor(pos)`,
   `scrollIntoView: true` (CM auto-centers cursor).
7. CodeMirror's selection-set update fires → § 5.1 syncs preview
   anchor to the new cursor line.

### 5.3 Click in editor

Already a CodeMirror native action — selection-set update fires §
5.1 path. No new wiring.

### 5.4 Tick rendering

`alignment-ticks.js` `paintStrip`:

- Editor cursor tick Y: unchanged (still uses `coordsAtPos` for
  cursor head — cursor is always in viewport).
- Preview cursor tick Y: was computed from
  `cache.tops[cursorOrdinal]`. New: bridge supplies the
  interpolated line doc-Y in the same `cursorTickY` field. Module
  unchanged.

## 6. Edge cases

| Case | Behavior |
|------|----------|
| Single-line block (heading, hr) | `L1 == L2` → fraction = 0; equivalent to block-top sync. |
| Cursor on blank line between blocks | `lezerBlockIndexAtPos` returns nearest preceding block; fraction may exceed 1 if line > L2 → clamp fraction to [0, 1]. |
| Block missing from `cache.blocks` (count mismatch with editor) | Existing min(k, cache.length-1) clamp; behaves like block-top alignment for clamped index. |
| Block element without `data-sourcepos` (admonish wrapper, runtime-injected chrome) | Use block-top fallback (no interpolation). |
| Preview block has nested elements (math, mermaid) with their own bounds | Click handler walks UP to top-level body child only — same as today. Interpolation is over the outer block's height. |
| Cursor in cover-page front-matter | Not represented in lezer/preview blocks. Fallback to scroll position 0. |
| Long fenced code block | Linear interpolation works well — uniform line height on both sides. |
| Auto-correct (v0.2.3 path) | Currently disabled in v0.2.3 ship. If re-enabled, `currentBlock` and drift detection stay scrollTop-anchored — independent of the cursor-line tick rendering. |

## 7. Risks

1. **Visual jitter on text wrap.** Editor wraps long lines via
   CodeMirror's `lineWrapping` extension; preview wraps via HTML
   browser layout. The mapped line may sit several pixels off the
   "same content" on the other side. Acceptable: still shows the
   right neighbourhood.
2. **Math-heavy blocks misalign.** A `$$ … $$` display-math block
   spans multiple source lines but renders as a single tall image in
   preview. Linear interpolation puts a target line midway through
   the source span at the visual center of the math block — usually
   fine for "I'm somewhere in this math".
3. **Cursor jump from preview-click changes scroll on both sides.**
   Existing cursor-sync logic already handles this; risk is double
   smooth-scroll feeling sluggish. Reuse `SMOOTH_LOCKOUT_MS` to
   prevent bounce-back as today.

## 8. Implementation order (SDD)

1. Spec section per § 4–6. (this file)
2. **Tests** (frontend/tests/line-anchor.test.mjs):
   - Pure interpolation function `lineYInBlock(L, L1, L2, blockTop, blockHeight)`.
   - Source-line-from-click `lineFromClickY(clickY, height, L1, L2)`.
   - Edge cases: L1 == L2, L outside [L1, L2], height = 0.
3. **Implementation** in `app.js`:
   - Refactor `syncPreviewFromCursor` to use line-level anchoring.
   - Refactor `syncEditorFromPreviewClick` to compute target line
     before dispatching CodeMirror cursor jump.
   - Update bridge.getEditorState / bridge.getPreviewState to supply
     interpolated `cursorTickY` instead of block-top `cursorTickY`.
4. **Manual smoke**:
   - Click mid-paragraph in preview → editor cursor lands at that
     paragraph's nearest source line.
   - Cursor-arrow within a paragraph → red tick advances down the
     preview side at proportional rate.
   - Snap-to-end (Cmd+Down) lands at last source line, preview
     scrolls to last block.
   - Display math click → editor cursor jumps to math's first
     source line (fraction collapses to 0 when L1 == L2 typically).
5. **Commit per task**, atomic.
