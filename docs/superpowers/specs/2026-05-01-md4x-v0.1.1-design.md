## 1. What md4x is

md4x converts a single Markdown file to a PDF with magazine-quality typography and layout. The target user is a writer fluent in markdown who does not want to wrestle with formatting tools but wants output that looks like it came from The New Yorker, The Economist, or a Springer textbook. Future versions will add PPTX and MP4; both are out of scope for v0.1.1.

**md4x is a tool that uses an LLM at specific pipeline stages, but it is not an agentic tool.** No agent loop, no tool use / function calling, no MCP. LLM calls (which appear in future formats — none are present in v0.1.1) are plain prompt → completion.

The Markdown file is the canonical source of truth. Each output format is a *projection* of that source, not an independent artifact.

## 2. v0.1.1 scope

### In scope

- Convert any markdown file with mermaid, KaTeX/math, code blocks, tables, lists, and embedded images / SVGs to a beautifully-typeset PDF.
- Three bundled templates: `magazine`, `swiss`, `stem`. User-supplied templates loadable from disk.
- Single binary, ~6 MB target, portable copy-as-install.
- macOS and Windows.
- No external runtime deps for the v0.1.1 feature surface — the OS-provided WebView is the only system service used.

### Explicit non-goals (deferred to v0.1.x or later)

PPTX/MP4 output; Linux support; PlantUML; multi-file projects; live preview / watch mode; front-matter config; full graceful-error UX; PDF metadata; TOC bookmarks; deterministic output; citations; WASM plugins; graphviz/kroki; template authoring tools; auto landscape page rotation; splitting massive diagrams; compressed-for-email mode.

See `docs/backlog.md` for the prioritized deferred list.

## 4. Architecture

### 4.1 Microkernel + plugin trait

The core knows nothing about specific renderers, dialects, or templates. It performs four orchestration steps:

1. Parse markdown to AST (via `comrak`).
2. Walk the AST; for each renderable element, dispatch to a registered plugin that handles its content type.
3. Assemble the result into a single HTML document.
4. Hand the HTML to the renderer plugin → PDF.

The plugin contract is a single Rust trait. Each plugin declares which content types it handles and a transform function. Plugins are bundled at compile time via cargo features; default = all plugins on.

### 4.2 Plugin loader categories

| Loader | Used for | v0.1.1 plugins |
|---|---|---|
| **In-tree Rust crate** | Pure-Rust transforms | `comrak` (markdown parser), `syntect` (syntax highlighting) |
| **Bundled JS in WebView** | Renderers with mature JS implementations | `mermaid.min.js`, `katex.min.js` |
| **Subprocess** | Renderers with no JS port and not on the v0.1.1 critical path | none in v0.1.1 (PlantUML in v0.1.x) |

A fourth loader — WASM — is reserved as a design slot but is not implemented in v0.1.1.

### 4.3 Rendering pipeline

```
foo.md
  ↓ comrak: markdown → AST
AST
  ↓ walk; replace mermaid/math/code blocks with HTML placeholders
HTML document
  ↓ template applies CSS, cover page, embedded JS for mermaid + KaTeX
HTML + bundled JS
  ↓ system WebView (WKWebView macOS / WebView2 Windows)
WebView executes mermaid + KaTeX in-page; smart-sizing JS classifies and
applies auto-fixes; diagnostics emitted to console
  ↓ WebView print-to-PDF API
foo.pdf
```

Critical consequence: **mermaid runs inside the same WebView that produces the PDF, not in an external puppeteer subprocess.** md4x bundles `mermaid.min.js` and a small JS glue layer; the WebView does the rest. This is what makes the "single binary, no external installs" promise real.

### 4.4 Renderer-as-plugin

The HTML→PDF renderer itself is a plugin. v0.1.1 ships one renderer plugin: WebView-based (WKWebView + WebView2 abstracted via a `wry`-style trait, with platform-specific PDF-export glue).

Future renderers (Typst, etc.) become additional renderer plugins without architectural change. Templates are renderer-tagged: a `magazine` template targeting WebView+CSS is one artifact; a future Typst rewrite of the same look would be a separate artifact under the same name.

## 6. Templates

### 6.1 Template package shape

A template is a directory containing:

```
templates/<name>/
  template.toml      # metadata: name, target renderer, font fallback chain
  style.css          # prose, headings, tables, lists, code, blockquote
  mermaid.json       # per-template mermaid theme variables
  cover.html         # cover page HTML snippet with placeholders
  sample.md          # representative input demonstrating the template
  preview.pdf        # baseline rendered output (used for snapshot tests)
```

### 6.2 Three bundled templates

| Template | Aesthetic | Body type | Heading type | Accent |
|---|---|---|---|---|
| `magazine` | Editorial / longform (New Yorker / Atlantic feel) | Iowan Old Style / Charter, justified, drop caps | SF Pro / Helvetica | Magazine red `#b91c1c` |
| `swiss` | International Typographic Style | Helvetica, ragged-right, no drop caps, sectional numbering | Helvetica Bold | Terracotta `#a85a2a`, with right-edge color block on cover |
| `stem` | Academic / textbook | Charter, justified | Helvetica Bold | Navy `#1e3a5f`; theorem callouts; numbered chapters |

All three are embedded in the v0.1.1 binary via `include_bytes!`.

### 6.3 User-supplied templates

`md4x INPUT.md --to pdf --template-dir ./my-style/` loads any directory matching the template package shape. The renderer validates `template.toml`, `style.css`, and `cover.html` are present.

## 7. Mermaid behavior (US-7 + US-8 partial)

### 7.1 Classification

After mermaid renders each block in the WebView, the JS glue layer measures the natural SVG dimensions and classifies by effective scale ratio:

| Class | Trigger | Action |
|---|---|---|
| `fits well` | scale ≥ 0.85 | render at default size, done |
| `fits w/ effort` | 0.43 ≤ scale < 0.85 | apply fontSize bump (1.4×), re-render once, accept |
| `won't fit readably` | scale < 0.43 | try semantics-preserving auto-fix; if none works, emit diagnostic |

Page content area: 628 × 951 px (A4 portrait, 22 mm margins, 96 DPI). Min readable text: ~6 px (mermaid default 14 px × 0.43 scale).

Strategy by aspect:
- 0.7 ≤ aspect ≤ 1.4 → fit-bounds (limited by min(width-fit, height-fit))
- aspect > 1.4 → fit-width
- aspect < 0.7 → fit-height

### 7.2 Auto-fix strategies

Tried in order; first strategy that produces `fits well` or `fits w/ effort` is used:

1. **Direction flip** — for `flowchart LR/RL` ↔ `TB/TD`; for `stateDiagram-v2` `direction LR/TB`.
2. **fontSize bump** — multiply `themeVariables.fontSize` by 1.4×, re-render.

ELK layout swap was tested on the GEOMAN corpus and rejected (worse aspect ratios on the test cases). It is not in the v0.1.1 strategy ladder and is parked on the backlog for case-specific use in v0.1.x or US-9.

### 7.3 Per-block fence hints

Authors may override defaults via fence attributes:

````
```mermaid {layout: "wide", scale: 1.4, min-text: "9pt"}
flowchart LR
  A --> B
```
````

Supported v0.1.1 hints:

| Hint | Type | Effect |
|---|---|---|
| `layout` | `"auto" \| "natural" \| "wide" \| "tall"` | overrides aspect-based strategy selection |
| `scale` | float `1.0..2.0` | multiplies internal fontSize before render |
| `min-text` | size string (e.g. `"7pt"`) | custom escalation threshold |

Hints are parsed off the fence info string and stripped before passing source to mermaid.

### 7.4 Diagnostics

When a diagram falls into `won't fit readably` and no auto-fix works, md4x emits a warning to stderr:

```
diagram-N (line L): WON'T FIT — <reason>
  Suggestion: <type-specific recommendation>
```

For `sequenceDiagram` with many participants: "split into 2+ diagrams (no semantic-preserving auto-fix exists for sequence diagrams)."

For `flowchart` already in TB direction: "try `flowchart LR` or split content."

### 7.5 Per-template mermaid theming

Each bundled template ships its own `mermaid.json` matching the prose aesthetic:

| Template | fontFamily | primaryColor | corners |
|---|---|---|---|
| `magazine` | Iowan Old Style or Helvetica | `#b91c1c` | slight radius |
| `swiss` | Helvetica | `#a85a2a` | sharp |
| `stem` | Helvetica or Charter | `#1e3a5f` | slight radius |

## 8. CLI

```
md4x INPUT.md --to pdf [-o OUTPUT.pdf]
              [--template NAME | --template-dir PATH]
              [--keep-work]
```

| Flag | Meaning |
|---|---|
| `--to pdf` | Output format. Required. (PPTX / MP4 not in v0.1.1.) |
| `-o, --output PATH` | Output path. Default: `<input-stem>.pdf` in the input file's directory. |
| `--template NAME` | Selects a bundled template. One of `magazine`, `swiss`, `stem`. Default: `magazine`. |
| `--template-dir PATH` | Loads a user-supplied template directory. Mutually exclusive with `--template`. |
| `--keep-work` | Preserves the scratch dir after success (for debugging). Mirrors the bash `KEEP_WORK=1` env var. |

Examples:

```sh
md4x report.md --to pdf
md4x report.md --to pdf --template swiss
md4x report.md --to pdf --template-dir ./my-style/
md4x report.md --to pdf -o /tmp/out.pdf
```

## 9. Testing discipline (load-bearing)

Per the testing rule in `CLAUDE.md`: every behavioral claim gets a test that mechanically verifies it. v0.1.1 test plan:

### 9.1 Per-template regression tests

For each of `magazine`, `swiss`, `stem`:
1. Render `templates/<name>/sample.md` to PDF.
2. Assert page count matches the recorded baseline.
3. Assert each mermaid block is classified as recorded (fits well / w/ effort / won't fit).
4. Assert text size of the largest body paragraph is within tolerance of baseline (extracted via PDF parsing).
5. Snapshot test: page 1 (cover) compared to baseline PNG via perceptual diff. Tolerance set to ignore font-rendering minutiae but catch layout breaks.

### 9.2 Mermaid integration test (regression-prevention against real-world doc)

Single hard-coded reference: `misc/GEOMAN_ARCHITECTURE.md`.
1. Render with default template.
2. Assert classification: 3 diagrams `fits well`, 4 `fits w/ effort`, 3 `won't fit readably` (matching the empirical baseline established 2026-05-01).
3. Assert auto-fix moves diagram-01 from `won't fit` to at least `fits w/ effort` (effective text size ≥ 6 px).
4. Assert stderr contains diagnostic warnings for the two sequenceDiagrams that won't fit (#02, #10).

### 9.3 Plugin trait unit tests

Mock plugins implementing the trait verify:
1. Core dispatches each content type to the registered plugin.
2. Multiple plugins registering for the same type — first-registered wins (deterministic).
3. Plugin output is concatenated in source order.
4. A plugin returning an error produces a diagnostic and does not crash the core.

### 9.4 CLI tests

End-to-end shell tests:
1. `md4x foo.md --to pdf` produces `foo.pdf` in the same directory.
2. `--template swiss` selects the swiss template (verified via PDF metadata or snapshot diff).
3. `--template-dir ./templates/swiss` produces output equivalent to `--template swiss`.
4. Missing input file returns non-zero exit code with helpful stderr.
5. Specifying both `--template` and `--template-dir` returns an error.

## 10. Deployment & distribution

Per the **portable CLI principle** in `CLAUDE.md`:

- Single binary, ~6 MB target. Bundled `mermaid.min.js` (~3 MB), `katex.min.js` + fonts (~700 KB), three template asset packs (~30 KB total CSS + JSON), Rust deps statically linked.
- Build: `cargo build --release` with `opt-level = "z"`, LTO, strip, `panic = "abort"`.
- Distribution channels (v0.1.1): GitHub releases (`.zip` per platform); `cargo install md4x` for Rust toolchain users.
- Optional later (not v0.1.1): Homebrew formula, Scoop manifest, code signing.
- macOS: ad-hoc signed binary; user may need to override Gatekeeper on first run.
- Windows: unsigned `.exe`; user may need to dismiss SmartScreen on first run.

Uninstall: delete the file. No system state to clean up.

## 11. Open implementation questions (resolved during plan-writing)

These details are intentionally left for the implementation plan to settle; the design does not lock them:

1. Exact `wry` integration shape — single renderer plugin with internal platform branches, or one plugin per platform?
2. Plugin trait method signatures — sync vs async; allocation patterns.
3. JS glue layer ↔ md4x diagnostic surface — console capture vs explicit DOM signals (e.g., a `<div id="md4x-diagnostics">` the host reads after print).
4. `comrak` extension set enabled by default (footnotes yes; tables yes; citations no in v0.1.1).
5. Cargo workspace layout — single crate, or core + per-plugin crates.
6. Where the JS bundles physically live in the repo (`assets/js/`, `crates/md4x/assets/`, etc.).
7. How `--template NAME` resolves bundled templates at runtime (compile-time `include_dir!` vs runtime extraction to a temp dir).
