# v0.2.4 — Self-contained markdown via inline macros

**Status:** backlog (next after v0.2.3 ships).
**Layer:** plugin (`crates/md4x-core/src/plugins/macros.rs`).
**Hard constraint:** kernel (`md4x-core/src/render.rs`, `lib.rs`) must
not learn about this. All logic in the macros plugin per project's
kernel discipline.

---

## 1. Problem

Today, KaTeX user macros for a markdown file `foo.md` live in a sibling
`foo.macros.json`. Two artifacts must travel together for correct
render. Easy to lose one. Easy for collaborators to miss.

After the GUI's "undefined macros → generate template…" workflow
populates the JSON, the user is left choosing:

- Ship `foo.md` + `foo.macros.json` together (status quo).
- Manually paste the JSON into the markdown and hope nothing breaks.

Neither is great. We want a **self-contained `.md`** option.

## 2. Goal

After macros are resolved into `<filename>.macros.json`, prompt the user
to choose **inline** (single-file) or **sidecar** (existing two-file)
delivery. Both renders must produce byte-identical PDFs.

## 3. UX

When a `.macros.json` exists alongside a `.md`, GUI offers a one-shot
action: **"Inline macros into document"**. CLI gets `md4x macros inline
<file.md>` and `md4x macros split <file.md>` as inverse operations.

Inline:
- Reads `<file>.macros.json`.
- Wraps the JSON content inside a fenced YAML-front-matter-style block
  at the top of the markdown.
- Optionally deletes the sidecar JSON (asked).

Split (inverse):
- Extracts the inline block back into `<file>.macros.json`.
- Removes the block from the markdown.

## 4. Inline format (proposed)

YAML front-matter is the lightest precedent. Use a dedicated
**md4x-macros** front-matter section. Format:

```
---md4x-macros
{
  "\\R":   "\\mathbb{R}",
  "\\eps": "\\varepsilon"
}
---
```

Properties:

- Sentinel `---md4x-macros` (line-anchored). Distinct from generic
  `---` YAML so we never collide with Pandoc/Jekyll metadata. Plugins
  unaware of it leave it alone.
- Body is **strict JSON** (not YAML), to share the parser/format with
  the existing `.macros.json` files. Round-trip is trivial.
- Closing line is bare `---`.
- Block must be the very first thing in the file, before any other
  content (including a generic YAML front-matter; if both are present,
  the macros block must come first or last — pick once and hold).
- A `.md` file may contain at most one such block.

## 5. Plugin behavior

`macros` plugin (existing) extends to:

1. On document load, scan for the sentinel block at file head. If
   found:
   - Parse JSON body.
   - Merge with sidecar `.macros.json` if both present (sidecar wins on
     conflict, with a warning — user can opt to flip via setting).
   - Strip the block from the source before passing markdown to the
     parser, so it never reaches the renderer.
2. Provide CLI subcommands `inline` / `split` (via the plugin's CLI
   surface — kernel just dispatches).
3. GUI exposes the action in the undef-macros modal once the JSON is
   non-empty.

## 6. Render guarantee

Inlined and split forms must produce byte-identical PDFs. This is the
acceptance test:

```
cp foo.md inline.md
md4x macros inline inline.md
md4x render foo.md     -o foo.pdf
md4x render inline.md  -o inline.pdf
diff foo.pdf inline.pdf  # exit 0
```

## 7. Open questions (for spec finalisation)

- Sentinel exact spelling: `---md4x-macros` vs `---!md4x-macros` vs
  `<!--md4x-macros-->`. HTML-comment form survives editors that
  hard-rewrap front-matter; YAML form is more discoverable.
- Conflict policy: sidecar wins, inline wins, or merge with explicit
  per-key precedence?
- Should `inline` also embed mermaid theme JSON, syntect themes, or
  other plugin sidecars? Possibly via a more general "embedded
  sidecars" mechanism (generalised front-matter section per plugin).
  Decide before locking the format.

## 8. Why this is a follow-up, not a v0.2.3 task

v0.2.3 is scoped to the scroll-alignment ticks UX. Macros
self-containment is a parser/format change that touches the macros
plugin and adds CLI subcommands. Independent surface area.
