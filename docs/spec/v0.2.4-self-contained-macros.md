# v0.2.4 — Self-contained markdown via inline macros

**Status:** spec locked. Implementation pending v0.2.3 ship.
**Layer:** plugin (`crates/md4x-core/src/plugins/macros.rs`).
**Hard constraint:** kernel (`md4x-core/src/render.rs`, `lib.rs`) must
not learn about this. All logic lives in the macros plugin per the
project's kernel discipline.

---

## 1. Problem

KaTeX user macros for `foo.md` live in a sibling `foo.macros.json`.
Two artifacts must travel together for correct render. Easy to lose
one. After the GUI's "undefined macros → generate template…" workflow
populates the JSON, users want a single self-contained `.md` they can
ship.

## 2. Goal

Provide a one-shot **inline** action that embeds the JSON inside the
markdown via an invisible block, plus an inverse **split**. Both forms
must produce byte-identical PDFs. Distribution semantics: inlined `.md`
is enough on its own.

## 3. Non-goals

- Not a generic front-matter system for v0.2.4. Embedded-sidecar
  generalisation (other plugins) is deferred to a future version once a
  second plugin needs it (§ 9).
- No automatic inlining on save — user-driven only.

## 4. Inline format

**HTML comment block, at end of file:**

```markdown
<!-- md4x:macros
{
  "\\R":   "\\mathbb{R}",
  "\\eps": "\\varepsilon"
}
-->
```

Properties:

- Sentinel `<!-- md4x:macros` must start at column 0 of its line.
- Closing `-->` must start at column 0 of its line.
- Body between sentinels is **strict JSON** (same parser/format as the
  sidecar `.macros.json`).
- Block is **at the end of the file**. Anything after it is rejected
  by the linter (single trailing newline allowed).
- A `.md` may contain at most one such block.

Why HTML comment + EOF placement:

- Comment is invisible in every markdown processor — Pandoc, Jekyll,
  GitHub renderer, mdBook. No leaked JSON in the PDF or any other
  rendering target.
- EOF placement keeps the user's working content's line numbers stable
  when the block is added or removed.

## 5. Plugin behavior

`macros` plugin (extended):

1. **Load.** On document load, scan from EOF backward for the closing
   `-->` and matching `<!-- md4x:macros` sentinel. If found:
   - Parse JSON body.
   - Merge with sidecar `.macros.json` if both exist:
     **inline wins** on per-key conflict.
   - Strip the block from the source string before passing markdown to
     the parser. The renderer never sees it.
2. **CLI.** Plugin contributes the `macros` subcommand (kernel just
   dispatches):

   ```
   md4x macros inline <file.md>   # read sidecar → append inline block at EOF
   md4x macros split  <file.md>   # extract inline block → write sidecar
   md4x macros show   <file.md>   # print effective merged map
   md4x macros lint   <file.md>   # report inline/sidecar divergence
   ```

   `inline` keeps the sidecar by default; `--delete-sidecar` opts in to
   removal. The GUI flow always keeps the sidecar (§ 6).

3. **Pretty-print on inline.** JSON body emitted with 2-space indent
   and stable key ordering (lexicographic). Diffability is a primary
   concern — version-controlled `.md` should yield clean diffs after
   `inline`.

4. **Lint** reports any per-key divergence with severity `WARN` so
   `md4x render` doesn't fail the build, but `md4x macros lint`
   exits non-zero on divergence.

## 6. GUI integration

- **Undef-macros modal.** Once `.macros.json` is non-empty, the modal
  gains an action: **"Inline into document"**. Click → plugin's
  inline operation runs → `.md` is rewritten → small toast: *"Macros
  inlined. You can distribute this .md on its own. The sidecar is
  kept for editing."*
- **Sidecar is always kept** in the GUI. `--delete-sidecar` is
  CLI-only.
- **Help menu.** A new menu item **"About inline macros"** opens a
  popup styled like the Export PDF dialog with a short explanation:
  what inline does, what split does, what the lint warning means.

## 7. Documentation

- **README**: a "Self-contained markdown" section explains the inline
  workflow, the file format (HTML comment + JSON), and the precedence
  rule (inline wins on conflict).
- **`md4x macros --help`**: full subcommand surface with
  one-paragraph rationale on the conflict rule.
- **GUI help popup**: matches README content, summarised.

These three surfaces must agree on the conflict rule wording — change
together.

## 8. Round-trip guarantee

`inline → split → inline` produces a byte-identical `.md` modulo a
single trailing newline normalisation. Acceptance test:

```
cp foo.md a.md && cp foo.md b.md
md4x macros inline a.md
md4x macros split  a.md && md4x macros inline a.md
diff a.md b.md   # exit 0 (after canonicalising trailing newline)
```

PDF acceptance:

```
md4x render b.md -o sidecar.pdf
md4x render a.md -o inline.pdf
diff sidecar.pdf inline.pdf   # exit 0
```

## 9. Future generalisation (deferred)

The same comment-block pattern fits any plugin sidecar:

```
<!-- md4x:<plugin-name>
<plugin-defined body>
-->
```

When a second plugin (mermaid theme, syntect theme, …) needs embedded
sidecar support, lift the parser into a shared "embedded sidecar"
helper consumed by individual plugins. Don't lock the namespace
prematurely — `macros` is the only registered name in v0.2.4.

## 10. Implementation order (SDD)

1. Spec section per § 4–8.
2. Tests:
   - **Format parser**: extract & strip inline block; reject
     well-known malformed cases (sentinel mid-line, multiple blocks,
     block not at EOF, invalid JSON).
   - **Merge precedence**: inline beats sidecar on conflict.
   - **Round-trip**: inline ∘ split ∘ inline = identity.
   - **CLI subcommands**: integration tests for inline / split / show
     / lint.
   - **PDF byte-equivalence**: render both forms, hash output.
3. Implementation in `plugins/macros.rs` until tests pass.
4. GUI button + popup + menu wiring.
5. README + `--help` text.
6. Side job: convert `crypto-book.md`'s sidecar → inline as the first
   real-world test of the workflow.

## 11. Side job

After v0.2.4 lands, run `md4x macros inline crypto-book.md` to
transform the user's reference book into the first self-contained
artifact. Verify PDF unchanged. Keep the sidecar JSON in the repo as
the "split" reference.
